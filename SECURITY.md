# Security policy

## Supported versions

Until the first stable release, security fixes are applied to the current default branch only. Published alpha versions may change without backward-compatibility guarantees.

## Reporting a vulnerability

Do not open a public issue for a vulnerability, leaked credential, proprietary DLL, license material, or customer optical design.

After GitHub publication, use the repository's private vulnerability reporting feature at:

`https://github.com/YonggangG/Zemax_MCP_Server/security/advisories/new`

Until that channel exists, contact the future repository owner privately. Include the affected version, reproduction steps using non-proprietary data, impact, and suggested remediation. Do not attach licensed OpticStudio files or assemblies.

## Threat model

This server gives an MCP client access to a local engineering application. Depending on the enabled tools, an authorized caller may:

- launch or attach to OpticStudio and consume a license seat;
- open, modify, optimize, save, or overwrite optical systems;
- read local installation metadata and configured paths;
- create analysis output and use significant CPU or memory;
- interact with a user-open system when extension mode is selected.

MCP input is untrusted, even when generated by a model. Run the server only for trusted local clients, review tool calls that have destructive or expensive effects, and keep backups or source control for optical designs.

## Deployment guidance

- Run as a non-administrator user whenever possible.
- Restrict filesystem permissions to the projects the server needs.
- Prefer standalone mode for isolated automation; understand that extension mode can alter the system open in the UI.
- Do not expose this stdio server directly to a network.
- SSE and streamable-HTTP transports or bridges should bind to a loopback interface by default. Any remote exposure requires authentication, TLS, authorization and access controls, request limits, and security auditing.
- Do not put secrets, license keys, proprietary optical data, or personally identifying information in MCP configuration committed to source control.
- Treat paths, filenames, catalog names, operand definitions, and all tool parameters as untrusted input at system boundaries.
- Set execution limits for long analyses and optimizers where the implementation provides them.
- Review logs before sharing them; they may contain local paths, lens metadata, or error details from ZOS-API.

## Dependency and supply-chain policy

Runtime dependencies are resolved from `pyproject.toml` and locked by `uv.lock`. CI installs from the lockfile and does not download OpticStudio components. Release artifacts must not contain:

- `ZOSAPI.dll`;
- `ZOSAPI_Interfaces.dll`;
- `ZOSAPI_NetHelper.dll`;
- OpticStudio executables;
- glass catalogs or proprietary sample systems;
- API license files, activation data, or credentials.

Before publishing a release, inspect both source and wheel contents. Run `twine check` once its supported Core Metadata versions include the version emitted by the build backend; Twine 6.2 currently stops at 2.4 while this toolchain can emit 2.5.

## Live testing

Live tests may consume a license seat and change application state. They are excluded from public CI and must require an explicit `live_zemax` selection on a licensed Windows workstation. Use disposable copies of systems and close or save user work before running extension-mode tests.
